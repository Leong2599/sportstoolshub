The source footer had five blocks: a brand block, then "Fitness Calculators" (6 links), then
"Performance Trackers" (11 links), then **"Performance Trackers" again** (11 links), then
"Nutrition Tools" (13 links). All 41 tool links were there; only the heading was duplicated.

The footer is now built from the catalog's categories - one column each - so the heading can only

| Column | Heading | Links |
|---|---|---|
| 1 | Sports Tools Hub | brand description, no tool links |

## Why the chrome lives in `themeConfig` and not in `src/theme/*`

The ticket's file estimate listed `src/theme/Navbar/*` and `src/theme/Footer/*`. The implementation
uses the theme's own components through `themeConfig` instead, fed by `src/data/chrome.ts`. The
reason is the mobile sidebar:

- `theme-classic`'s `Navbar/Content` and `Navbar/MobileSidebar/PrimaryMenu` **both** read
  `themeConfig.navbar.items` directly.
- Swizzling only `Navbar/Content` would render the catalog items on the desktop bar while the
  hamburger menu kept showing the old items - the ticket's "mobile menu matches source behavior"
  criterion would fail.

Keeping the items in `themeConfig` means the desktop navbar, the dropdown, and the mobile sidebar
all read one catalog-derived list, and the theme keeps its own dropdown, keyboard and sidebar
behaviour. The footer follows the same route, which also gives the brand block and the
copyright/sitemap line that the source has.

`src/data/chrome.ts` stays pure and framework-free (no React, no Docusaurus runtime import), so it
is unit-testable and safe to import from the config at build time.

## What the catalog drives

```ts
buildNavbarItems(catalog)  // -> Home, Tools (dropdown), Blog, About
buildFooterColumns(catalog)// -> one column per category, one link per tool
```

- The navbar dropdown has one entry per catalog category, pointing at the home page anchors
  `#fitness-calculators`, `#performance-trackers`, `#nutrition-tools` (source behaviour).
- Every footer link is `/tools/<slug>` for a catalog tool, labelled with the catalog title.
- `buildCategories()` drops a category that has no tools, so the dropdown and the footer stay in
  step.
- The anchor ids live in `src/data/chrome.ts` (`TOOLS_ANCHOR`, `CATEGORY_ANCHORS`) and are imported
  by the home page, so the dropdown targets and the page sections cannot drift apart.

## Navbar order

The source order was Home / About / Tools / Sports Blog. The ticket specifies Home / Tools / Blog /
About, and that is what shipped. The dropdown, the mobile menu and the footer all use the new order.

## The `/about` route

The navbar links to `/about`, and the route did not exist - it is ST-25's scope. Under
`onBrokenLinks: 'throw'` a link to a missing route fails the build, so ST-23 could not ship the
About item without the route.

`src/pages/about.mdx` ports the source `about.html` content (hero, mission, what we offer, tool
categories, values, call to action) onto the site's existing page shell. The source's mojibake icon
glyphs are dropped, as everywhere else.

Side effect: the two legacy aliases that were still missing are now emitted. The alias count went
from 256 to 258 and **missing went from 2 to 0** - `/about.html` and `/tools/about.html` both
resolve to `/about`.

## Deviations from the plan

- **No `src/theme/Navbar/*` or `src/theme/Footer/*` swizzles.** The theme's own components are
  driven through `themeConfig`, which is fed by `src/data/chrome.ts`. The reason is the mobile
  sidebar (see above): a partial swizzle would leave the hamburger menu out of sync with the
  desktop bar. The ticket's criterion - theme components fed by `src/data/tools.ts`, no
  hand-maintained tool links, mobile menu matching the source - is met; the file layout differs
  from the estimate.
- **The About page was pulled forward from ST-25.** ST-23's own acceptance criteria require an
  About navbar item, and `onBrokenLinks: 'throw'` makes a link to a missing route a build
  failure. ST-25 keeps the branded 404 page and the remaining assets (hero, og image, favicon set,
  CNAME, robots.txt).
- **The home page was touched.** The dropdown anchors had to exist somewhere, and the source points
  them at the home page. The page now renders the four anchor headings and a plain list of the
  catalog tools. **ST-24 replaces this page and has to keep the anchor ids** - they are exported
  from `src/data/chrome.ts` (`TOOLS_ANCHOR`, `CATEGORY_ANCHORS`) so the home page can import them
  instead of hard-coding strings.
- **The brand logo was copied into `static/img/`** (`images/logo.png` -> `static/img/logo.png`,
  512x512). ST-23 needs it for the navbar brand; ST-25 owns the rest of the assets.
- **Footer labels follow the catalog, not the source footer.** Nine source labels differ from the
  tool page titles: "Cycling Power Tracker", "Injury Risk Calculator", "Tennis Match Energy
  Calculator", "Training Load Calculator", "Meal Timing Calculator", "Micronutrient Checker",
  "Pre-Workout Nutrition", "Post-Workout Recovery" and "Weight-Cut/Gain Planner". The footer uses
  the catalog titles (one source of truth, and the same text the tool pages and the sitemap use).
  The source footer also linked to absolute legacy `.html` URLs; the new footer links to the
  internal routes.
- **The sitemap link is a plain anchor.** `/sitemap.xml` is a generated file, not a route, so a
  Docusaurus `Link` to it would be reported as a broken link and fail the build. The bottom line is
  injected as HTML, as in the source.

## Issues encountered

- The first cut of `ChromeNavbarItem` was a union without `type?: undefined` on the plain-link
  member, so `item.type === 'dropdown'` did not narrow the type and the tests failed to compile.
  The optional-undefined member fixed the narrowing.
- The About page reuses `ToolPage` from `src/components/calculators/` as its page shell because
  that component already provides the hero + content layout the source About page has. The name is
  about tools, so ST-25 may want to extract a neutral page shell when it polishes the page.
